# Trace Protocol

## 目标

满足女儿学习需求：记录一个真实应用如何由人和 agent 协作完成。

## Trace 类型

| 类型 | 位置 | 用途 |
|---|---|---|
| Session Trace | `07_traces/sessions/` | 记录一次完整协作过程 |
| Decision Trace | `07_traces/decisions/` | 记录重要产品或技术选择 |
| Tutorial | `07_traces/tutorials/` | 整理成给女儿看的学习材料 |
| Template | `07_traces/templates/` | 记录模板 |

## 何时记录

默认规则：

- M 每次完成重要交互、任务回收、W 确认或文档固化后，都应记录原始 trace。
- 原始 trace 是协作工作日志，不等于最终给女儿看的展示稿。
- 阶段结项时，再从原始 trace 中筛选、整理成 Tutorial 或阶段复盘。
- M 不应每次询问 W 是否记录；除非 W 明确说“先别动”或本轮已超过允许改文件范围，否则默认记录。
- 敏感信息不进入 trace，包括 Cookie、密钥、服务器凭据、私人账号信息和不应公开的个人隐私。

必须记录：

- MVP 范围确定。
- 技术栈确定。
- 开发环境搭建。
- 架构设计完成。
- 测试策略确定。
- 关键代码阶段完成。
- 重大问题被定位和解决。
- W 修正 M/P/I/Q 的理解或工作机制。
- P/I/Q worker 输出被 M 回收、整合并经 W 确认。

可以不记录：

- 单纯拼写修改。
- 无决策、无长期价值的临时探索。
- 无长期价值的小调整。

## Session Trace 内容

每份 session trace 至少包含：

- 目标。
- W 的输入。
- M 的理解。
- 任务拆解。
- 执行过程。
- 关键决策。
- 验证。
- 结果。
- 给女儿看的解释。

## Decision Trace 内容

每份 decision trace 至少包含：

- 决策。
- 背景。
- 备选方案。
- 最终选择。
- 原因。
- 影响。
- 给女儿看的解释。

## 写作要求

- 不只是日志，要解释为什么。
- 不夸大 agent 能力。
- 保留人的判断和取舍。
- 说明失败、限制和风险。
- 让学习者看到需求如何变成软件。
