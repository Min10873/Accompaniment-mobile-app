# Product Design V2 Draft

## 状态

已确认并部分落地，作为后续父辈界面和 worker task 的产品基准。

来源：

- `00_inbox/thinks/think8.md`
- 2026-05-17 W 与 M 关于音频上传、父辈页逻辑和 UI 风格的讨论

## 产品定位

这是一个给父辈使用的智能伴奏工具。

它不只是“从抖音提取音频”，而是帮助用户完成一个更自然的目标：

```text
我想得到一个音频，并把它变成适合演奏/合唱使用的伴奏。
```

## 核心用户视角

父辈打开页面时，只有两种情况：

1. 手里没有音频，只有抖音视频或链接，需要系统帮忙获取音频。
2. 手里已经有音频，需要上传后播放、下载或变调。

因此首页不应围绕技术流程组织，而应围绕“我现在有没有音频”组织。

## Page 1：初始页

目标：

```text
得到一个音频
```

已确认结构：

- Page 1 和 Page 2 必须分开；进入处理、结果或失败状态后隐藏 Page 1。
- Page 1 使用两个 tab，而不是上下堆叠两个入口：
  - `抖音链接`
  - `上传音频`
- 默认打开 `抖音链接`。
- 两个入口互不干扰，避免父辈同时看到两个流程。

### 入口 A：从抖音提取

适用场景：

- 用户手里没有音频。
- 用户在抖音里看到一个视频。
- 用户复制了抖音分享文本或链接。

页面重点：

- 让用户知道在哪里粘贴。
- 让用户知道怎么粘贴。
- 让用户知道点击后会生成可以播放和下载的音频。

必须能力：

- 粘贴抖音分享文本或链接。
- 明显的“粘贴链接”按钮。
- 明显的“开始生成”按钮。
- 失败时用人话提示。

### 入口 B：上传已有音频

适用场景：

- 用户手里已有伴奏音频。
- 用户希望上传后变调。
- 可能是 W 先帮父辈准备好音频，再让父辈使用页面调整或下载。

建议范围：

- 支持单文件上传。
- 支持 `mp3`、`m4a`、`wav`。
- 文件大小先限制为 `20MB`。
- 上传入口显示 `歌曲名字` 输入框。
- 选择文件后，前端默认用文件名去掉扩展名填入歌曲名字。
- 用户可以手动修改歌曲名字。
- 后端保存显示用 `title`，但实际音频文件仍使用随机文件名保存，不保存用户原始文件名或本地路径。
- 上传文件保留 7 天。
- 上传后进入同一个结果页。
- 上传后也可以播放、下载、复制链接和变调。

暂不做：

- 批量上传。
- 在线剪辑。
- 多音轨编辑。
- 歌名搜索。
- 云盘管理。
- 账号系统。

### 首页结构

```text
伴奏提取

[抖音链接] [上传音频]

Tab: 抖音链接
- 粘贴链接
- 分享文本输入框
- 开始处理

Tab: 上传音频
- 选择音频文件
- 歌曲名字
- 上传音频
```

首页应默认突出“从抖音提取”，因为这是当前已验证主流程。

上传入口可以作为第二入口，不抢主任务。

## Page 2：结果页

目标：

```text
使用当前音频
```

结果页可能来自两种路径：

- Page 1 从抖音提取完成。
- Page 1 上传音频完成。
- Page 2 自己生成了一个变调版本。

不管来源如何，用户来到结果页时，核心事实都是：

```text
这里已经有一个当前音频。
```

已确认结构：

- Page 2 顶部使用 `伴奏已准备好`，不使用 `处理好了`。
- Page 2 顶部显示歌曲名字。
- Page 2 使用两个 tab：
  - `播放保存`
  - `变调处理`
- 默认打开 `播放保存`。
- 播放/下载/复制和变调处理分开，避免高级功能压过核心操作。

## Page 2.1：当前音频面板

用户目标：

- 播放当前音频。
- 知道当前音频是什么版本。
- 下载当前音频。
- 复制链接发给别人。
- 知道链接有效到哪天。

必须显示：

- 歌曲名字。
- 当前版本名称，例如：
  - 原调
  - 升高 1 个半音
  - 降低 2 个半音
- 音频播放器。
- 下载按钮。
- 复制链接按钮。
- 当前音频链接有效期。
- 当只有 `原调` 一个版本时，不显示版本切换条，避免出现两个 `原调`。
- 当存在多个版本时，显示可切换版本。

有效期规则：

- 有效期应跟当前音频文件走。
- 当前播放/下载哪个版本，就显示哪个版本的有效期。
- 前端短期可用 `audio_variants[*].created_at + 7天` 显示绝对日期。
- 更稳妥的长期方案是后端直接返回每个音频版本的 `expires_at`。

## Page 2.2：变调面板

用户目标：

- 当前音频太高或太低时，生成一个更适合演奏/合唱的版本。

必须能力：

- 选择升高或降低。
- 父辈 UI 默认只显示半音数 `1-5`。
- 后端可继续保留 `1-11` 能力，但父辈界面暂不暴露 `6-11`。
- 显示说明：`1 = 半音，2 = 全音`。
- 点击生成新版本。
- 能切回原调或已有版本。

设计原则：

- 变调是高级功能，不应压过播放和下载。
- “当前播放哪个版本”和“我要生成哪个版本”必须分开。
- 已有版本是切换操作，生成新版本是创建操作。

## Page 2 结构

```text
[返回首页]

伴奏已准备好
歌曲名字

[播放保存] [变调处理]

Tab: 播放保存
- 当前版本：原调 / 升高 N 半音 / 降低 N 半音
- 原生 audio 播放器
- 下载音频
- 复制链接
- 当前音频链接有效到 YYYY.MM.DD

Tab: 变调处理
- 当前基准：当前版本
- 升高 / 降低
- 半音 1-5，说明 1 = 半音，2 = 全音
- 生成这个版本
- 切回原调
```

## 歌曲名与下载命名

歌曲名规则：

- 后端 `TaskRecord` 和 `TaskResponse` 保存并返回 `title`。
- 上传音频时，前端默认从文件名去掉扩展名生成歌曲名，用户可修改。
- 上传音频未提供歌曲名时，使用 `上传的音频`。
- 抖音提取首版使用 `抖音伴奏` 作为兜底标题；后续如果 sidecar 稳定提供视频标题，再接入真实标题。
- 页面没有 title 时显示 `未命名伴奏`。

下载文件名规则：

```text
歌曲名-版本-歌伴侣.后缀
```

示例：

```text
后来-原调-歌伴侣.mp3
后来-升高2半音-歌伴侣.mp3
后来-降低3半音-歌伴侣.mp3
```

文件名安全规则：

- 去掉 `/ \ : * ? " < > |` 和换行。
- 合并连续空格。
- 标题过长时截断。
- 空标题用 `未命名伴奏`。

实际存储规则：

- 服务器实际音频文件仍使用随机文件名。
- 不保存用户原始文件名或本地路径。
- 下载名由前端 `download` 属性生成。

## 音频水印

首版同时采用两种轻量水印：

- 文件名水印：下载名包含 `歌伴侣`。
- metadata 水印：音频 metadata 写入 `comment=from LFAPP`。

metadata 规则：

- 抖音提取生成 mp3 时写入。
- 变调生成 mp3 时写入。
- 上传音频在 ffmpeg 可处理时尽力写入；如果 metadata 写入失败，不阻断上传成功。

不做：

- 不添加可听片头/片尾水印。
- 不改变音频内容来做可听品牌提示。

## UI 风格方向

W 希望父辈觉得页面先进、酷、有面子，愿意在人前展示。

当前待外部视觉探索：

- W 已让 Gemini 网站生成 UI 风格方案。
- M 后续负责审查 Gemini 输出是否符合父辈可用性，并把可取部分落到现有前端。
- Q 已完成 Gemini UI 草案可用性审查：视觉方向有仪式感，但对 80 岁老年用户存在过度设计、视觉干扰、暗色可读性、技术术语和触控密度风险。
- P 已完成 Gemini UI 产品评审：黑金/控制台/舞台感值得借鉴，但必须去掉英文、夸大宣传、复杂自定义播放器和过密变调网格。

建议视觉关键词：

- 智能伴奏台。
- 专业伴奏控制台。
- 专属音乐工作室。
- 舞台灯感。
- 高级音频设备。
- 大字、大按钮、强主次层级。

需要避免：

- 像后台管理系统。
- 像廉价表单工具。
- 字太小。
- 对比度不足。
- 装饰压过操作。
- 复杂导航。
- 难懂英文。
- 过度使用暗色小字。
- 使用 `user-select: none` 影响复制和粘贴。
- 使用 Tailwind CDN、Google Fonts 等外部运行时依赖。
- 使用“无损”“AI 算法”“发烧级”“指定助手”等可能夸大或难懂的文案。
- 自定义播放器替代原生 `<audio controls>`。
- 半音按钮过密导致误触。

已确定文案规则：

- 使用：`智能伴奏台`、`专业伴奏控制台`、`专属音乐工作室`、`高品质伴奏提取`、`智能音频处理`、`云端音频处理中心`。
- 不使用：`发烧级`、`金牌控制台`、`Hi-Res`、`无损`、`AI 算法`、`指定助手`。
- 核心功能按钮和状态提示使用纯中文。
- 可以营造高级感，但不能承诺实际不存在的音质、算法或认证。

## UI 可用性约束

后续如果采用 Gemini 的黑金高级感方向，必须做简化版，而不是直接使用 Gemini HTML。

必须满足：

- 主文字和背景对比度足够高。
- 重要文字字号不小于 `16px`。
- 核心功能按钮使用纯中文。
- 核心操作优先：粘贴、开始、播放、下载、复制、返回首页必须最明显。
- 装饰元素不能抢主操作视觉焦点。
- 相邻按钮保持足够间距，单个触控目标不小于约 `44px`。
- 变调后必须用文字明确显示结果，例如“当前播放：升高 2 个半音”。
- 剪贴板按钮必须有长按粘贴兜底提示。
- 播放器必须保留或包裹原生 `<audio controls>`，不使用复杂自定义播放器替代。

建议吸收 Gemini 的部分：

- 黑金/舞台控制台的高级感。
- 分区卡片。
- 抖音提取和上传音频双入口。
- 当前音频与变调面板分离。
- 半音说明。
- 教程弹窗思路。
- `抖音提取` 主卡片带“推荐”角标，`上传已有音频` 作为次要卡片。

不建议吸收 Gemini 的部分：

- 旋转黑胶唱片。
- 跳动 VU 表作为主要视觉。
- 密集 1-11 半音网格。
- 英文状态和徽章。
- 复杂自定义播放器。
- 夸张宣传词。

## Page 1 UI 规范

标题建议：

```text
歌伴侣
专业伴奏控制台
```

或：

```text
智能伴奏台
```

入口 A 是主入口：

```text
从抖音提取伴奏
```

元素：

- 推荐角标。
- 粘贴输入框。
- `粘贴链接` 按钮。
- `开始生成` 或 `开始提取` 按钮。
- `不会复制抖音链接？` 教程入口。

入口 B 是次入口：

```text
上传手机里的音频
```

元素：

- 支持格式说明：`mp3/m4a/wav`。
- 大小限制说明：`20MB 以内`。
- 上传按钮。

## Page 2 UI 规范

顶部：

- 右上角 `返回首页`。

当前音频卡片：

- 当前版本，例如：`原调`、`升高 2 个半音`。
- 原生 `<audio controls>` 播放器。
- `保存伴奏到手机` 或 `下载音频`。
- `复制链接发给微信好友` 或 `复制链接`。
- 当前音频链接有效期，使用绝对日期。

变调卡片：

- 标题：`调整音高` 或 `变调`。
- 方向：`升高`、`降低`。
- 默认半音选择：`1`、`2`、`3`、`4`、`5`。
- 说明：`1 = 半音，2 = 全音`。
- 操作：`生成这个版本`。
- 已有原调时显示 `切回原调`。

半音范围决策：

- 后端可继续支持 `1-11`。
- 父辈 UI 默认只展示 `1-5`，减少误触和选择压力。
- 暂不做 `6-11` 高级入口；如果真实使用需要，再新增“更多”。

## UI 验收补充

后续视觉改造必须用 Playwright 截图检查：

- iPhone SE 尺寸下 Page 1 和 Page 2 的关键操作是否可见。
- 长标题或长链接是否撑破布局。
- 粘贴按钮失败时是否显示长按粘贴提示。
- 半音选择在窄屏下是否仍能准确点击。
- 当前播放/下载和变调区域是否分得清楚。
- 版本号、任务号和有效期是否弱化但可读。

## 上传后端草案

I 已返回最小实现建议，详见：

```text
02_vibe/results/I-UPLOAD-BACKEND-PLAN-01.result.md
```

建议采用：

- `POST /api/uploads`。
- 请求类型：`multipart/form-data`。
- 字段：`file`。
- 文件类型：`mp3/m4a/wav`。
- 文件大小：`20MB`。
- 成功后复用现有 `TaskRecord`。
- 上传成功可以直接创建 `done` 状态任务。
- 创建 `audio_variants.original`。
- 上传结果进入同一个结果页。
- 继续复用现有 pitch 流程。
- 后端应返回 `expires_at`，不让前端只用 `created_at + 7天` 推算。

M 建议：

- 首版上传保留原格式，不做转码。
- 上传成功直接返回 `201 Created + status=done`。
- 统一使用随机文件名，不保留用户原文件名。
- `source="upload"` 用于区分上传来源。
